# Limits

What Jefe does not do, what the evidence does not show, and where it can be wrong. No benchmark number is repeated here; the figures are in the marker blocks of [README.md](../README.md) and [bench/README.md](../bench/README.md), written from result files.

## Cost

- **Any saving is for expensive sessions.** The design moves the typing off the model your session runs on. If that model is already cheap (Sonnet, Haiku), Jefe is expected to cost more than the same model alone, because the plan, the interview and the review are extra work (this is the design's expectation; the sessions-on-a-cheaper-model table, once the benchmark script has filled it, shows whether it holds). On such a session you get verification and a fresh-context builder, not a lower bill.
- **A fixed cost per job.** The planner reads the skill text and spends a few turns whatever the size. The smallest jobs can cost more than the model alone. This is why quick one-offs are done plainly, without Jefe, and why the small-task row of the benchmark is labelled "not what Jefe is for".
- **Cost claims describe the default helper models.** If you pick other helper models ([USAGE-LEVELS.md](USAGE-LEVELS.md#helper-models)) or change the planner with `/model`, the figures do not apply.
- **Costs are API-equivalent.** They are Claude Code's own `total_cost_usd` per run. What a subscription plan actually charges against your usage window is a different quantity.
- **Background helpers cost the planner extra turns.** The skill tells the planner to run helpers in the foreground. In the live runs Claude Code still ran them in the background and ended the planner's turn while they worked, so a message such as "the scout is still running, I'll wait" is true. Each result costs the planner one more turn (headless runs always wait). A plugin cannot change this. In a live test on Claude Code 2.1.327, setting `CLAUDE_CODE_FORK_SUBAGENT=0` inside the session did not stop the backgrounding, so Jefe recommends no setting. The size of the extra cost has not been measured.
- **The prompt cache.** Claude Code reuses text it has already sent (the prompt cache) and bills it lower. Its documentation says the cache lasts one hour for the main conversation and five minutes for a subagent on a subscription within plan usage, and five minutes for both on usage credits, an API key or a cloud provider; switching the model with `/model` discards it. Every Jefe helper is a subagent, so a helper that waits more than five minutes between turns starts again at full price. Jefe never switches a running session's model. A job resumed after a park is a new session, so its first turn pays full price for its context. Each benchmark run is a new `claude -p` process (with an API key by default, with a subscription login under `--auth login`, which the CI workflow uses), so it starts with an empty cache.
- **The number of helpers is a design choice.** By default up to three builders work at once, with one reviewer per job or stage (`hooks/levels.mjs`). No measurement backs these numbers yet. Each helper reads its brief and files in its own context, so more helpers cost more. The benchmark measures whole jobs, not single helpers.
- **Checks and git run from the project root.** The wrapper always passes `--root` and the scripts run from the project root, because `plan.md` and its stage checks live there. Run Jefe from the project root. From another folder `start` says so (`note: checks and git commands run from the project root <root>, not from this folder`); when the root is not a git work tree but the folder you started in is inside a repository below it, `start` says `note: the git repository is below the project root (<path>); start Jefe from that folder so commits and base work` and `base: none` stays.
- **A nested repository is not part of a Jefe job.** The gate's own git calls (status, diff, the commit's `git add -A`, the staged-changes check and the commit itself) skip a submodule, gitlink or embedded repository entirely: its `.git/config` programs cannot run, `finish --commit` does not stage or commit changes made inside one or a submodule pointer moved to another commit, and an untracked nested repository does not keep the tree dirty for `push`. `finish` prints one `note:` line naming up to five paths it left alone. Commit those yourself, in that repository (and the outer pointer, if you want it).
- **A filter the repository configures is not run, and `finish --commit` refuses files that use it.** `git lfs install --local` writes `filter.lfs.clean`, `.smudge`, `.process` and `.required` into the repository's own `.git/config` (local scope), so Jefe treats them as the repository's: it does not run them, and a commit that would stage a path with `filter=lfs` is refused (`commit: NOT made (...)`), because staging it without the filter would store the real binary instead of a pointer. If you use a locally installed LFS, commit those files yourself, or install it for your user (`git lfs install`, which writes your global configuration; the gate leaves your own filters active). Status, size and the stamp still work; such a file can only look modified there. A file committed through such a filter can also look changed to the gate when it is not, because git re-reads a file whose time stamp is not older than its index (typical right after a clone or checkout), and the gate's git has the filter switched off; `finish --commit` then refuses it. Run `git status` yourself once so git refreshes its index, or define the filter in your own global configuration.
- **A repository nested in a project is its own project.** A submodule, a vendored clone or a git worktree (Claude Code's own under `.claude/worktrees/` too) inside a project is its own project when the session's folder is inside it: what was approved at Go for the outer project does not apply there, and Claude Code asks as it normally would. Writes to paths inside it from a session whose folder is the outer project are judged as before. While the session's folder is inside the nested repository, the outer project's helper rules and permit log do not apply either (Claude Code's ordinary prompt decides, and in a headless run that means the call is denied). The end-of-session clean-up and the report check look at the nested repository, so the outer project's `ending` approvals stay until they expire.
- **The home folder is a project only when you start in it.** From `~/notes` it is not found; `start` in the home folder says so (`note: the project is your home folder: the tests and the secrets scan cover everything in it, and Jefe approves no file writes here (Claude Code asks for each of yours; helpers' writes are refused): for a job that needs helpers to write files, start Jefe in a project folder`). In such a project the hook approves no file write, because shell start files, ssh keys and git configuration live there: Claude Code asks you for each write the main session makes, and helpers' writes are refused, so a job that needs helpers to write files does not work there. Start Jefe in a project folder.
- **The write block list and file-system folding.** The block list is compared on a folded form of every name (Unicode compatibility and case folding, combining marks and invisible characters removed) as well as the typed one, and on the name the file system reports for the part that exists. A file system whose folding rules differ from these (other Unicode versions, trailing dots or spaces on Windows volumes, short 8.3 names) can still reach a blocked name by a spelling the hook does not fold. On NTFS an alternate data stream name (`CLAUDE.md::$DATA`) is not recognised as the blocked file.
- **The Go command is recognised by the script's name in the command text.** That includes quoted and wildcard spellings: quotes or backslashes inside the name, `jefe` followed in the same word by a glob, brace, backtick or `$` expansion (following the shell's quoting), a glob that matches `.jefe/bin/jefe-gate` or one of its folders (`.j?fe/b?n/j?fe-g?te`, `cd .j*/b*n`), and any word containing `.jefe/bin`. Written plainly or in one of those spellings, the Go command always gets the prompt, in auto mode too. Plainly: inside one simple command, a word built by a variable, a command substitution, a backtick or `$'...'` escapes that is the program (also behind a prefix or launcher such as `timeout 9` or `stdbuf -o0`) or holds a `/` (`X=jefe; .$X/bin/$X-gate go`, `"$G" go`), together with a later word `go` or `allow` (quotes removed), gets the prompt, whatever stands between them and whatever program it turns out to be; so `"$HOME/bin/tool" go` and `cp "$SRC/a" go` are asked about as well, and so is a `go` after `--`, which the gate does not read as a grant. A command over 8000 characters is asked about without being read when it names a Jefe script, holds a glob character (`?`, `*`, `[`), or holds an expansion character (`$` or a backtick) and the word `go` or `allow`; any other command that long is left to Claude Code's own permission rules. A command that hides the name some other way (brace expansion spread over the path such as `.j{e,}fe/bin/j{e,}fe-gate go`, text decoded and piped to a shell, a script defined earlier) is decided by Claude Code's own permission rules: in manual mode it still prompts or, for a helper, is refused; in auto mode the classifier decides; with a broad allow rule, that rule decides. Text scanning cannot catch, and so leaves to Claude Code's own permission rules, the grant word itself held in a variable, `eval`, a shell function or alias defined earlier in the command, a here-string or `sh -c` with the name passed as an argument, input piped to `xargs` that holds the name, and a command substitution whose output is the whole command. A session that can run any shell command without a prompt could also write Jefe's approval record directly, because it is a plain file in the registry folder (`run/<key>.allow.json` under `~/.claude/jefe`, or `JEFE_HOME`). So Claude Code's permission layer is the real boundary, and Jefe cannot be stronger than it.
- **A case-insensitive volume.** On a case-insensitive volume (the Mac default) a typed path whose letter case differs from the real one gets its own approval key, because the key is a hash of the path as the system reports it. It fails safe: that spelling has no approvals, so nothing is approved there; type the real spelling. The home folder itself is compared without regard to letter case, so such a spelling never makes your home folder a project.
- **No account entry for your user** (some containers): the home folder, which is never a project root, is then taken from `HOME`.
- **A gate path with a space is a known limit.** The skill calls the gate unquoted. From the project root `start` prints the short `.jefe/bin/jefe-gate`; when it has to print an absolute path through a folder whose name contains a space, that call breaks. Run Jefe from the project root.
- **Thorough costs more.** It adds reviewers and fix rounds. The benchmark shows whether that bought more passed tasks; do not assume it did.
- **Savings are not promised outside the tables.** A job where the top model alone would have finished in a few quick turns may not be cheaper with Jefe.

## What "verified" means

- **The script check proves that the tests and checks ran and passed.** It does not prove they are good tests. A project with weak tests gets a weak gate. The gate reads what the test runner reports, so test code written to misreport its own results (a Go `TestMain` that silences the testing package's output and exits 0, for example) can make a failing suite read as passing; reading the diff is the check for that. With no tests, the builder writes a few first, and the gate says `gate: PASS (no tests found, no checks given)` if nothing exists, which Jefe reports as "nothing was tested".
- **The secrets scan is pattern-based.** It is a net for common mistakes, not a guarantee; the formats it knows and what it skips (and says so) are listed under Limits in [SECURITY.md](../SECURITY.md#limits). A text file over 32 MB is scanned only in part, so the gate says `INCOMPLETE` for it; `finish --commit` scans everything it is about to commit again (lock files, dependency paths and binary files included, with the allowlist as it was at the job's start) and commits exactly what that scan read, never the working tree; it leaves a file over 32 MB, binary or not, out of the commit with a `commit: left out ...` line (commit it yourself); it also leaves untracked key stores (`.p12`, `.pkcs12`, `.pfx`, `.keystore`, `.jks`, `.der`, `.p8`, `.ovpn`) out.
- **The reviewer is a model.** It can miss a real defect and it can raise a false one. It may say `review: GAP` only with evidence, which reduces false alarms and does not remove them. A reviewer is never the agent that built the work.
- **The gate is enforced by the skill, not by Claude Code.** The model runs `jefe-gate finish` because its instructions say to. Jefe's own Stop hook only sends the planner back once if its final message lacks the gate's `gate:` line, and only after a passing gate: `finish` records the line to check only for a passing gate line, so after a FAIL a final message that claims PASS is not checked. What it guarantees: the gate's own line is in the final message, or the planner is sent back once (one exception: while a review is pending, unless `allow --clear` or a push ended the approvals after the report was recorded, a final message with neither a `review:` line nor the `gate:` line looks like an interim turn and is not sent back). It also sends the message back when another line states a different verdict in one of two forms: `gate:` followed by the word PASS, FAIL or INCOMPLETE anywhere in a line (`all good, gate: PASS` beside `gate: PASS (tests not run)`; one verdict is read per line, the first), or a line that begins (after list, quote and heading marks) with at most one word, then `Gate`, at most two more words, a separator and a verdict word (`**Gate:** ✅ PASSED`, `Gate result → FAIL`, `Gate: OK`); the gate's own pasted lines are not read as claims. That is a net for a careless summary, not a guard against other wording: a sentence (`The gate passed.`), a heading with the verdict on the next line, a table, a checked task-list box before a line of the second form (`- [x] Gate: PASSED`), or any phrasing outside those two forms is not caught, so the line to read is the gate's own. A Stop hook that you configure to run your command is a stronger guarantee on that one point.
- **The gate is not a sandbox.** Tests and checks run with your permissions. Each runs in its own process group, which the gate kills at the time limit and when the command ends; a process that leaves that group (a daemon started in its own session, for example with `detached: true`) is not stopped, and a check that starts one and exits 0 passes while the daemon keeps running.
- **Read the first report of a new kind of job closely.** The gate shows only that the checks it was given ran and passed. The reviewer judges the change against the goal, not the running result. Neither notices a goal misread the same way in the brief and the checks, a check too weak to fail, or a visual result nobody looked at. So read one report, open the changed files and run the result yourself before you leave that kind of job to run unread.

## Permissions

- **The promise, exactly.** One permission prompt at Go. After it Jefe asks for nothing: the commands you approved are answered by the hook; anything else is left to Claude Code. In auto mode its classifier judges that; in manual mode a helper's call is refused and listed as skipped. "Nothing runs that was not approved" is true in manual mode only. How the layers stack: [SECURITY.md](../SECURITY.md#how-the-layers-stack).
- **An approved script runs whatever it holds.** `--allow-cmd "sh lint.sh"` approves the file, not its contents: a change to `lint.sh` during the job runs unasked, as a change to the project's tests does.
- **Auto mode.** Commands outside the Go list are decided by Claude Code's classifier, whose rules come from your own or managed settings and not from Jefe. Seen with Jefe in five sessions on 2026-11-18 and 2026-11-19 ([what was seen live](#what-was-seen-live-and-what-was-not)).
- **`claude -p`** starts in manual mode (Claude Code 2.1.302 and newer), and a call that would need a dialog is denied. Jefe grants nothing there; pass `--permission-mode auto` or `--allowedTools`.
- **`/sandbox`** covers Bash only. The gate writes its registry under `~/.claude/jefe` (or `JEFE_HOME`); under `/sandbox` that write fails unless the folder is among the sandbox's writable folders. Untested.
- **Claude Code Projects threads** load no plugins, so Jefe does not run there. A cloud session does not load plugins either ([DESKTOP-AND-CLOUD.md](DESKTOP-AND-CLOUD.md)).
- **A push is bound to what was tested and to the address in the Go command, not to the project's own code.** The gate pushes only the tested commit, only to the branch fixed at Go (the `go --branch` one, else the branch current at Go), after a plain `gate: PASS`, from a repository whose git configuration needs nothing beyond a plain push. That guards against a misled planner or helper and against the repository's git configuration and hooks. Tests, a check script or an approved command run as you and could rewrite the approval record or the remote: on a repository you do not trust, do not approve tests and a push together; read the code, use `/sandbox` (add the registry folder to its writable folders; untested), or push yourself. `--review pass` is the planner's claim, recorded but not verified, and the gate cannot control the receiving server's hooks ([SECURITY.md](../SECURITY.md#push)).
- **Approvals last for the job.** They end as described in [SECURITY.md](../SECURITY.md#when-approvals-end): at `allow --clear`, a new `go`, `park` or 12 hours after Go, earlier once the job's last check has passed. Details of the state files: [HANDOFF.md](HANDOFF.md). `JEFE_PERMIT=off` switches the hook off. Jefe writes no settings file.
- **Two Jefe installs at once** (a `--plugin-dir` checkout and the installed copy) write different wrappers; the hook approves only its own install's wrapper, so the other's calls prompt until `start` or a `/jefe` prompt rewrites it.
- **Headless runs get no approvals from Jefe.** `start` and `go` approve nothing there; the launcher passes the tools the job needs (the benchmark uses `Bash Write Edit Read Agent`).
- **Providers are text-only.** `jefe-gate ask` sends text and gets text back (no tools, no code changes); free models may train on what you send, so nothing private goes to them ([PROVIDERS.md](PROVIDERS.md)). `--in` limits which files can be attached, not the question text, and the secrets scan is a best effort.

### Project rules

Jefe writes no settings into your project. For your own repository, deny rules for real env files and home secrets are worth having; a cloud session reads only the committed `.claude/settings.json`. This repository's own file is a template (`.claude/settings.json`); copy only what suits you:

```json
{ "permissions": { "deny": ["Read(.env)", "Read(.env.local)", "Read(~/.ssh/**)", "Read(~/.aws/**)"] } }
```

## Evidence

- **Few trials.** Cells with fewer than three trials are marked "direction only" in the tables. Read the trials column.
- **Tasks were written by the author.** The six project tasks were each audited by a separate AI agent that checked every hidden assertion against the written specification, but the author chose the kinds of work. The held-out tasks (two job-sized, two project-sized, one small) were not used while the skill was being tuned (the author's statement; nothing in the repository proves it). Their results are in their own table ([bench/README.md](../bench/README.md#results)), from one run with one trial per task: a direction, not a finding.
- **The hidden tests are within reach of a session.** A run's session has unrestricted Bash on the same machine or runner whose checkout holds `bench/tasks/*/hidden/` and `solution/`, so a session could read them (the same for both arms); moving those folders out of reach during a run is not done yet.
- **The public sample is not the official harness.** It is 12 SWE-bench Verified instances run in plain virtual environments, not Docker, so scores are not comparable with the leaderboard. The tasks may be in the models' training data, which inflates pass rates for every arm alike. Most are modest issue fixes. It is a cross-check on the cost comparison, not a ranking.
- **Results come from one setup per table.** Each table's Method line names where it ran (`environment:`): so far the author's Mac or a GitHub Linux runner, with one account and one Claude Code version. Until a table block has been filled by the benchmark script it says so, and no figure on any page is typed by hand. Filled results may not carry over to your machine. Prices and model behaviour change.
- **A task set is a sample.** A different set of jobs could give a different answer. `bench/README.md` lists what would change the conclusions.

## Gaps in the benchmark method

Each is checked against `bench/run.mjs` and the task files; the details are in [bench/README.md](../bench/README.md#limits-of-the-method).

- **The interview is not measured.** Jefe arms get the answers in a scripted `ANSWERS:` block, so the cost of a real interview is not in any figure.
- **The plan-usage guard is off on Jefe arms** (`JEFE_USAGE_GUARD=off`). A real session may be downshifted or parked; a benchmark run is not.
- **The baseline gets no gate and no review.** The comparison is "same task, same pass test", not "same process".
- **A pass counts tests the model itself added.** The whole test command runs, and it includes them.
- **Prices come from a file kept by hand,** `bench/prices.json`, dated 2026-11-17. The dollar figure is Claude Code's own `total_cost_usd`; the file is a fallback and a cross-check.
- **The skill text was tuned on the 13 development tasks.** Only five tasks are held out.
- **The example command in `bench/README.md` and the runner's defaults differ.** The example asks for 3 trials and a 200 USD total; the defaults are 1 trial and 20 USD in total, with a stop at the cap.

## What was seen live, and what was not

Seen: four live runs on 2026-11-18 and 2026-11-19 (version 0.1.0, macOS, terminal, interactive; Claude Code 2.1.327 for runs A and B, 2.1.328 for runs C and D). A script checked each session against its screen captures and Jefe's files. Runs A, B and C were on earlier code; run D was on the code of this release.

Run A, ten scenarios: 65 checks passed, 0 failed. In the eight sessions that approved Go, the Go prompt (the `go` command with its `--allow-kind` and `--allow-cmd` arguments) was shown once and no other permission prompt followed: seven in manual mode, one in auto mode. One session declined Go on purpose and nothing started. Two scenarios did not follow the harness's script to its end: in the project scenario the mid-job remark was never typed, because the stages finished first; in the one-off scenario the harness missed the moment of the edit, and the checker then found the edit done directly, with no Go prompt and no Jefe files.

Run B repeated the four scenarios that end in a commit or an approved command, on later code: 27 checks passed, 1 failed. In one session the planner's Go command approved `sh lint.sh` and left out the project's test suite, so that job ended with `tests: not run (the project's test suite was not approved at Go)`, said so in its report, and showed `gate: PASS` on the approved check alone. Two things were changed after this run: the gate now prints `gate: PASS (tests not run)` in this case, and the planner's instructions say to approve the tests at Go when the project has a test command, unless you decline them. The planner still chooses what to ask for at Go, and what it leaves out is reported, not run.

Run C, the ten scenarios again on the code as it was first released into the maintainer's own setup: 65 checks passed, 0 failed. As in run A, the Go prompt was the only permission prompt in the eight sessions that approved Go (seven in manual mode, one in auto mode), and one session declined Go. The mid-job remark was typed this time. In the scenario where run B's planner had left the test suite out, it approved it. The one-off scenario again did not follow the script to its end: the harness missed the moment of the edit, and the checker found the edit done directly.

Run D, the ten scenarios on the code of this release, after the fixes from a review of the whole codebase: 59 checks passed, 5 failed, 1 did not apply. All five failures come from one session. In the first scenario the planner judged the task (`add a 'clear' command that removes finished todos`, three lines in two files) to be a quick job and did it directly, as its instructions allow for a change of a line or two: it said so, showed no Go prompt, ran no test and said it had run none. The scenario's checks expect a job, so they failed. That scenario was run again alone on the same code: the planner ran it as a job and 9 checks passed, 0 failed (one Go prompt, no other permission prompt, and the approvals ended by themselves after the job). In the other nine scenarios of run D every check passed: in the seven sessions that approved Go (six in manual mode, one in auto mode) the Go prompt was the only permission prompt, one session declined Go, the mid-job remark was typed, and the one-off scenario again did not follow the script to its end. The same task went through as a job in runs A and C, so which way a small task goes is the planner's judgement and can differ from one session to the next; ask for a check, tests or a commit in your request when you want the gate.

Auto mode (Claude Code's starting mode for interactive sessions from 2.1.283) was seen in five sessions on those two days (one each in runs A, C and D, two in earlier runs), each a job-sized task: the Go prompt was shown once and no other dialog appeared. In run A's auto-mode session the hook allowed 9 calls (project writes and gate calls), asked once and denied none; in run C's it allowed 10, asked once and denied none; in run D's it allowed 8, asked once and denied none. Claude Code's auto mode decided the rest.

No live run exercised what was added after run C: `go --resume`, a second test suite (pytest, `go test`, `cargo test`) next to a Node suite, the check of the push branch, the refusal of file-write approvals in a home-folder project. Unit tests cover them.

The desktop app (local session): the maintainer ran one job there on 2026-11-18, on version 0.1.0 before the latest fixes, and it passed its gate.

A helper's unapproved command refused without a prompt was seen in an earlier run the same day (three refusals in the project session). Runs A, B and C did not provoke it, because the planner had approved the command at Go.

The Stop hook did not fire in any session of the four runs that reached its report: each planner's last message already carried the gate line.

What the runs do not exercise is covered by unit tests only: a secret in a file whose type changed, the refusal to commit while a merge is in progress, the prompt for a very long command, and the `gate: PASS (tests not run)` line.

Not yet seen:

- The forced prompt for `go` over a rule of yours that pre-approves it (unit-tested only).
- The Stop hook sending a report back.
- Windows. Linux: no interactive job has been run on it; the headless benchmark jobs ran on GitHub's Linux runners, and the unit tests run there in CI (Ubuntu).
- A foreground helper. The skill asks for one, but in the live runs Claude Code started helpers in the background every time.
- The animated status line moving in a real session (it is drawn in text captures and as still frames only).

## Behaviour to know about

- **`finish --commit` commits the whole project folder, including changes made before the job.** It stages everything uncommitted (`git add -A -- .`, minus `.jefe/`, untracked files with secret-looking names, files over 32 MB and nested repositories), and an approved push then sends it. When `go` approves `git-commit` and the tree is not clean, it prints `note: N files were already changed before this job and will be in its commit: ...` (five names at most). The commit step then says `commit: includes N files that were already changed before the job`. Both notes come after you approved Go, and nothing is refused or left out for this: commit or stash your own work before Go. Commits you made on the approved branch before the job and have not pushed are pushed with the job's commit, and nothing names them: push or move them before Go. While a merge, cherry-pick, revert or rebase is in progress, it stages and commits nothing (`commit: skipped (...)`): finish or abort that first.
- **No spending limit.** Jefe has no budget setting. The plan-usage guard needs the status line and a plan usage window; with an API key, nothing in Jefe caps what a job spends while its approvals last (up to 12 hours).
- **Ending approvals at session end is best effort.** The SessionEnd hook that ends them has a 1 second timeout (`hooks/hooks.json`). If it does not finish, the approvals stay until the idle window or the 12 hour limit; run `allow --clear` to be sure.
- **`gate: PASS (no tests found, no checks given)` means nothing was tested.** So does `gate: PASS (tests not run, no checks given)`. Neither is a plain `gate: PASS`. `gate: PASS (tests not run)` means every check approved at Go passed and the project's test suite was not run because it was not approved at Go; it commits and pushes like a plain `gate: PASS`. When a project has two kinds of test and one of them runs no test (a `pytest.ini` with no tests next to a passing Node suite, or a Go module whose tests were all skipped next to one that passed, for example), the gate prints `tests: none found (<that suite's command>)` for it and the last line is still a plain `gate: PASS`, because the other suite passed: read the `tests:` lines, not only the last line. A check that ran no test (`check: none found`) never stands for a check given, but a passing check next to it still makes a plain `gate: PASS`. A check whose output is no recognised test report is judged by its exit code alone: a script that runs only skipped tests and prints no runner summary, or `go test -list`, passes. A check that reaches `go test` through another program (`make test`, `sh -c`, `nice`, a script) is not a pass when go test's own text is in its output, also behind a line prefix, because go test prints `ok <package>` and, with `-v`, `--- PASS` for a parent test, also when every test or subtest was skipped, and with no test file only a `[no test files]` line or, with `-cover`, a coverage line: it prints `check: none found (...)` and does not stand for a check given, unless another runner's report in the same output says a test passed. The gate knows go test's own lines in the forms the go tool prints them (package lines, coverage lines, verbose lines, benchmark and fuzz lines), also behind a line prefix, and a failure among them (a failed test, a panic, a build or vet error) is `check: FAIL` although the program exits 0. Give the `go test` command itself (with its packages and tags) as the check, which is read by its events; in a full run the project's own Go suite decides. When the wrapper hides or reformats go test's text (sends it elsewhere, keeps only part of it as `| tail -n 1` does, runs `go test -json`, or pipes it through a formatter such as gotestsum whose output is not go test's own text), the gate sees no test report and the exit code decides, as for any check: a check is a command you approved, and the gate cannot know it was meant to run tests. Another runner's failed test makes an exit-0 check `check: FAIL` only in the report the gate reads, the first one recognised (pytest before jest, so the check line of a Makefile that ignores a failing jest run and then runs a passing pytest is `check: PASS`); a failure in go test's own text is read wherever it is, so a Makefile that ignores go test's failure and then runs a passing pytest is `check: FAIL`, and a wrapper that retries go test and prints the failed first run is `check: FAIL` although the retry passed.
- **It stops, it does not wake itself.** At high context or plan usage it parks between stages and prints one command. You start the new session.
- **Context guard values are a judgement.** The default is the earlier of 120k tokens or 50% of the window on a 200K model, and 250k tokens on a 1M model. Published research says quality falls as input grows but gives no onset number, so this is an inference. Change it with `JEFE_CONTEXT_LIMIT` and `JEFE_CONTEXT_PERCENT`.
- **Plan-usage reading depends on the status line mod.** Without it the usage line says `usage: unknown` and the usage guard does not fire.
- **Not a yes-man.** If a suggestion would not help the goal, Jefe says so and lists it as "Suggested, not adopted". Say "do it anyway" to override.
- **Quick jobs are skipped on purpose.** One or two files with no design choice are done plainly, with no checks.
- **When the repository's git configuration cannot be read, the gate runs no git there.** A configuration that git cannot read (a timeout, a broken file, a hook out of time) is never treated as empty: `start` says `note: this repository's git configuration could not be read (...)` and the gate's git calls are off for that folder until it can be read. `start` and `go` stop there, because the gate cannot check for a tracked `.jefe` folder without git. They also stop when git cannot list the tracked files (a damaged index).
- **The list of git settings that can run a program is the one git 2.55 knows.** A later git may add more. `start` names the ones it recognises, and the gate's git calls run with the repository's other settings as they are.
- **Claude Code's experimental Code Mode is not supported yet.** In Code Mode (`CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`) a command can reach the permission hook as `cd '<folder>' && <command>`, a shape the hook never approves. So the gate calls, test commands and check scripts approved at Go lose their approval, and helpers' calls are refused. Nothing is approved that should not be: it fails safe, and the Go prompt still appears. `start` prints a `note:` when the variable is `1` or `true`, and the planner passes it on and carries on. The note cannot tell whether the session really runs in Code Mode: with the switch in your settings, a command inside the session sees `1` even when the session was started with `0`, so on such an account the note also shows in a plain session. A job started in a real Code Mode session fails safe at the first helper command. To run Jefe on an account that has Code Mode on, start the session with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=0 claude`. This was checked against the hook's code, not in a real Code Mode session.
