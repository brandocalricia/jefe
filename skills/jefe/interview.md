# Interview (interactive; a job or project starts with it)

1. Scout: one `jefe:researcher` (the `scout` model of the `models:` line), 100 words back; it changes nothing. Put the `files:` line of `start` in its brief: it reads `.jefe/files.txt` first when that line names it (with `not listed`, it lists the files itself), then uses Read and read-only search: the Grep and Glob tools where this Claude Code has them, otherwise one read-only command per call inside the project (`ls`, `find . -type f -not -path './.git/*'`, `grep -rn <text> .`), no pipes, relative paths. It reads the project's notes, README and contributing files and reports what is already written there: stack, test command, files the work touches, open decisions, a likely reference, any clearly better way, the stage split (project), and anything that cannot be undone, costs money or publishes.
2. Questions: AskUserQuestion, one question per call, 2-4 options in plain words, each saying what it leads to. Ask only when a different answer would change what gets built, the scout, the request and `prefs:` cannot answer it, and a wrong guess is costly or hard to undo; decide the rest and list it under `USUAL CHOICES:`. There is no fixed count: an obvious job needs none, a big or vague one is questioned along the seven parts (what and why, quality bar, tools, freedom, checks, delivery, goal), the question that changes the others first; a vague job (the person does not know what they want) always gets the direction question and the reference question. The first option is your pick, labelled "(Recommended)" with a reason; for a fact only the user knows (the reference) recommend none. Questions that usually apply:
   - Reference: "Is there something that already looks or works the way you want this to?" Options: no reference, a file or folder in this project, another project or product. It is the quality bar.
   - Git: leave uncommitted / commit locally (Recommended) / commit and push (only with a `push-to:` URL; with `none`, say a push cannot be approved); the branch on its own screen: new branch `jefe/<slug>` (Recommended) / current branch.
   - Helper model, only when the request does not already set it (words such as "opus subagents" or "helpers on sonnet" do): Defaults (Recommended) / All opus / All sonnet / Set one role. It applies to the helpers; your own model is the session's, which the user changes with `/model`.
   - The better-way question when the scout sees one; installs and live steps.
3. Go summary, plain text, no question, always printed before the `go` call whatever the job, one labelled line each: `END GOAL:`, `DONE WHEN:`, `OUT OF SCOPE:`, `REFERENCE:`, `ANSWERS:`, `USUAL CHOICES:`, `MODELS:` (only when not the defaults), `COMMANDS:` (`providers` only when `start` printed `providers:`), `INSTALLS:`, `LIVE STEPS:`, for a project `STAGES:` (a line per stage with its done-when), then a line per approval (`will run without asking: <tests command>`, `commit locally`, `push to <url>` from `push-to:`) matching the `--allow-*` flags below: `will run without asking` names only commands the Go command really carries. `LIVE STEPS:` names everything that cannot be taken back (push, publish, delete, send, spend) and what the scout flagged: that is what needs the user, and you decide and list the rest. A live step that matches an `ask` rule in the user's own permission settings still prompts after Go, so do not promise it runs unattended. `DONE WHEN:` holds a check that can run at the first stage; for a subjective result it says what good looks like and the reviewer looks at the real output. When `start` printed `test command: <command>`, the Go command carries `--allow-kind tests` and the summary names that command under `will run without asking`; only if the person said not to run them is it left out, and the summary has `TESTS: will not be run (you said so)`; a stage check that is not that test command needs its own exact `--allow-cmd` on the Go line; with `test command: none found` the summary has `TESTS: none found` and a `will run without asking` line for the check you plan instead; for work that is not code offer `check-script` (`sh .jefe/check.sh`, for example every claim has a source link and every number matches the sheet), which also approves what the helper writes into it. If the user changes something in text, re-print and redo step 4.
4. In the same message, one `<gate> go --goal "..." --done "..."` call plus the ones you have: `--out`, `--ref`, `--why "<12 words or fewer>"`, `--free`, `--answer k=v`, `--pref k=v` (standing answers), `--branch <slug>`, `--helpers <alias>` or `--helper-model <role>=<alias>` (repeatable; roles builder, reviewer, scout, runner; aliases sonnet, opus, haiku, fable), `--allow-kind <tests|git-commit|git-push|check-script>` per approved kind (`git-push` needs `--push-to <that url>`) (`providers` too, with `--allow-provider <name>`), `--allow-cmd "<exact command>"` per approved install or run command (one plain program with arguments, or `sh`/`bash` with one script file inside the project; never inline shell code, a wrapper, a network tool, pipes or operators: those go in `.jefe/check.sh` or under `COMMANDS:`), `--stage "<title> :: <done when>"` per stage. Its permission prompt is the Go button and the only prompt; if declined, say in one line that nothing was started and stop. Wait for its result before the first builder call.
5. Then the recipe in SKILL.md, with `finish --commit "<message>"` when the git answer says commit.

After Go, decide every open choice for the end goal and list it in the report; ask again only when there is no safe way forward at all; never ask about an irreversible step Go did not approve. What was not approved at Go is left undone and reported as `skipped: <what>` with the exact command for the user; do everything that does not depend on it.

When the user types something while the work runs, acknowledge it in one line and run one `<gate> amend` call as soon as you understand it, so the goal and plan files carry the change; the stage in flight is not restarted and approvals stay. Ask (one question per screen) only if it would change what gets built and could mean more than one thing. A remark that widens what helpers may change goes in `amend --note` and your later briefs; `FREE:` changes only with a new `go`.

Weigh every suggestion against END GOAL and DONE WHEN. If it would not help or would hurt (cost, risk, no checkable gain, scope creep), say why briefly, leave it out and say what you will do instead; say so too when a choice the user makes works against the goal. "Do it anyway" overrides. Record it with `amend --note "declined: <idea>: <reason>"`.
